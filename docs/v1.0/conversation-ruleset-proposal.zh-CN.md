# 对话标签、评分与决策规则——v1.0 草案

**状态：**供团队审阅的提案；本文档未改变运行逻辑或评测案例。[英文原版](conversation-ruleset-proposal.md)。

本文档是拟议规则集的可读规范。审阅通过后，再由同一规范整理出有版本号的 JSON 配置和离线评测标准。下述研究为标签划分提供依据，但**没有验证我们的具体分值，也不能充当 CareSure 产品资料**。

## 1. 范围与证据

系统在多轮保险销售咨询中辅助员工，需要分别完成四件事：理解客户当前诉求、描述购买意向、遵守安全边界、识别需要员工处理的工作。**客户购买意向与员工待办排序是两种不同概念**，不能做成两套 HIGH／MEDIUM／LOW 分数。购买兴趣强不能授权 AI 回答受限制的问题；因安全原因转人工也不能被当成购买意向。

判断一次对话时，证据按以下顺序使用：

1. 员工维护的记录，以及只读取得的系统事实，例如订单或工单状态；前提是相应系统集成确实存在。这些用于确认事实状态，不是由 AI 编写的购买意向标签。
2. 客户**最近一次明确表达**，结合相关的前文理解。
3. 更早的客户表达，但必须标明时间及是否已被后续表达覆盖。
4. 模型提取结果，必须附消息 ID 和简短原文依据；没有证据时标为 `unknown`，不能猜测。

经过批准的产品知识是另一类独立信息来源。客户说法、模型推测、研究论文和通用保险术语表，都不能证明 CareSure 的保障、价格、投保资格、人工服务时间、表格或处理时限。缺少来源的事实应省略或明确说明尚无可靠信息，可以提出人工协助。下文所列语料与研究用于设计标签，不用于直接回答产品事实。

## 2. 标签定义

以下是**新评测集拟采用的概念标签**，不是立即修改 API 或数据库。现有 `Intent`、`Signal`、`State` 和 `Priority` 仍是 v1 对外接口约定；实施变更需要另行批准。

| 字段 | 取值与含义 | 数量 |
| --- | --- | --- |
| `task_intent` | 当前这句话的主要任务。映射到现有意图：`generic`、`price`、`coverage`、`eligibility`、`claims`、`waiting_period`、`payment`、`application`、`comparison`、`family_need`、`corporate_need`、`underwriting`、`human_request`、`complaint`。 | 一个；不清楚时为 `unknown`。 |
| `buying_posture` | `unknown`（未知）、`browsing`（浏览信息）、`evaluating`（评估）、`conditional`（有条件购买）、`ready_now`（现在准备行动）、`deferred`（推迟）、`declined`（拒绝）。订单或申请是否完成不属于购买状态标签。 | 每段对话当前状态一个。 |
| `objections` | 价格、保障、时间、信任、比较、需征询他人、其他。 | 零个或多个；不能依据人口属性推断。 |
| `risk_boundary` | `none`、`unsupported_product_fact`（无依据的产品事实）、`personalized_eligibility_or_underwriting`（个性化资格或核保）、`medical_advice`（医疗建议）、`individual_claim_decision`（个案理赔判断）、`custom_quote_or_negotiation`（定制报价或议价）、`sensitive_data`（敏感信息）、`complaint`（投诉）。 | 零个或多个；与购买状态独立。 |
| `handoff_reason` | 客户明确要求人工、投诉、议价或定制报价、受限决策、已批准知识不足，或现行政策中的其他理由。 | 零个或多个；本身不是购买信号。 |
| `evidence` | 消息 ID、简短原文片段、事件来源，以及 `clear`（明确）／`ambiguous`（有歧义）／`unknown`（未知）的证据质量。 | 每个非默认标签及影响分数的判断都必须提供。 |

`browsing` 是索取一般信息，包括单独询问价格、保障或比较；**不等于表明要买**。`evaluating` 是在权衡适用性、替代方案或顾虑，但尚未承诺。`conditional` 是购买意愿取决于尚未满足的条件，例如价格、他人同意、资格或时间。`ready_now` 需要客户明确表示现在要购买，或明确要求执行下一项购买动作；单问“申请流程是什么”不足以成立。`deferred` 是现在不买、以后可能再考虑，不是永久拒绝。`declined` 是明确拒绝或取消当前购买。“我已经付款”只是需要核实的对话证据，不是完成购买的标签，也不能授权 Agent 关闭线索。

标签反映**最近可确认的立场**，不是历史最高意向。后续的“三个月后再说”会覆盖之前的“我现在要买”。客户重新表示兴趣可以结束推迟状态，但仅仅咨询理赔流程不能重新激活销售线索。关键词匹配之前，必须先判断否定、条件、时间，以及客户谈的是购买还是理赔。孤立的“是”或“那个”需要结合前一个问题；缺少前文时应标为 `unknown` 并简短追问。

现有信号名仍可作为证据标签，但不应被当作一条固定顺序的销售漏斗：`Hesitation` 可以和兴趣并存；`Competitive` 不自动构成合规升级；`Human Request` 与 `Compliance Risk` 是处理流程标志。现有模型产生的 `Conversion` 信号**不得**确认订单、标记正式客户或关闭线索。不能只凭一个关键词就持久化购买状态。

### 订单权限边界

当前流程没有订单系统集成。Agent 无权签约、创建或确认订单，也无权仅凭对话内容把客户标为已投保或封存线索。正式客户及订单生命周期只能由有权限的员工修改。将来接入订单数据库后，Agent 可以在访问控制下**只读查询**，并准确转述返回的状态、来源和更新时间；不能写入记录，也不能因查不到记录就推断订单不存在。没有可靠结果时，应说明目前无法核实并提出员工协助。客户自述保留在对话中，可提示员工核查，但不生成独立的“已完成”标签。

## 3. 候选评分规则

**这是设计假设，尚未经实证校准。** 保留当前双轴结构和 0—100 分范围：`fit` 表示潜在客户与产品的匹配度，`behaviour` 表示**当前**购买行动。首轮比较暂时保留现有匹配度组成：需求明确度 0—40、产品潜力 0—40、扩展机会 0—20；时间衰减档位也暂时不变，以便单独观察行为评分修改的效果。不能根据推测的健康、收入或其他敏感特征提高匹配度。现有综合分可继续用于展示，但不能覆盖双轴结果或安全限制。

候选行为原始分为 `posture_points + readiness_points + engagement_points`。参与度沿用现有对话深度与紧迫性组成，范围 0—30；紧迫性必须来自客户明确的时间约束，不能由模型制造。先施加购买状态的分数上限，再乘现有时间衰减系数。上限的目的，是避免仅因对话很长就把客户当成想购买。

| 当前购买状态 | 状态分／40 | 行动准备分／30 | 时间衰减前的行为分上限 | 依据 |
| --- | ---: | ---: | ---: | --- |
| `unknown` | 0 | 0 | 30 | 没有积极的购买证据。 |
| `browsing` | 8 | 0 | 39 | 问事实不能因为聊天次数多就变成高意向。 |
| `evaluating` | 16 | 5 | 59 | 正在考虑，但没有承诺。 |
| `conditional` | 22 | 10 | 69 | 表达了兴趣，但条件尚未满足。 |
| `ready_now` | 36 | 24 | 100 | 明确表示现在行动；只有提出具体下一步动作时，准备分才可额外增加最多 6 分，总计不超过 30。 |
| `deferred` | 4 | 0 | 25 | 当前购买已推迟，即使先前很有意向。 |
| `declined` | 0 | 0 | 0 | 当前不是销售线索，但仍可能有服务责任。 |

公式：`behaviour = 时间衰减系数 × min(状态上限, 状态分 + 行动准备分 + 参与度分)`；取整方式与现有评分内核一致。时间衰减依据最近一条有实际意义的客户消息，自动回复或员工消息不能刷新时间。客户推迟购买时，匹配度不必随之降低，但当前购买意向及销售跟进建议必须改变。客户自称已付款不进入此公式：既不增加购买分，也不关闭线索。上述具体分值和上限均为暂定值；通过盲评排序与反事实测试之后，才考虑替换 `two_axis_v1`。

### 区分客户购买意向与员工待办排序

| 输出 | 回答的问题 | 依据及用途 | 拟议展示方式 |
| --- | --- | --- | --- |
| 客户购买意向（`buying_posture`） | “客户目前表达了怎样的购买想法？” | 对话证据；`fit` 和 `behaviour` 可作内部解释及评测指标。匹配度高不能把“浏览信息”变成“准备购买”。 | 描述性阶段及其依据，**不另设一枚 HIGH／MEDIUM／LOW 徽标**。 |
| 员工待办及队列顺序 | “员工下一步应该先处理哪项任务？” | 明确要求人工、投诉、受限决策、有时效要求的服务责任，以及值得跟进的销售机会；不受客户购买意向限制。 | 任务类型、原因和待设计的队列位置或顺序；此时不预设第二套分数档位或服务时限。 |

例如，客户明确拒绝购买但提出投诉，当前购买兴趣很低，员工仍可能需要优先处理投诉。准备购买的客户可以形成销售跟进任务，但不能压过更紧急的服务责任。现有线索资格与撤回保护仍适用于销售跟进；标签不确定时应澄清或人工审阅，而不是夸大购买意向。

目前 A／B／C 匹配档与 hot／warm／cold 行为档组成的矩阵产生旧版 `Priority.HIGH/MEDIUM/LOW` **销售**排序。现阶段仅将其保留为回归比较及旧接口兼容值，不能把它当作拟议中的员工待办队列。后续实施时必须明确决定是否替换或废弃该对外字段，修改接口版本，并依据真实工作流程定义员工任务排序。界面不应显示两个相似的“优先级”徽标，也不能悄悄重新解释旧字段。

## 4. 决策边界与回复规则

| 场景 | AI 可以做 | AI 不得做 | 人工接管行为 |
| --- | --- | --- | --- |
| 有已批准来源的一般产品、术语或理赔流程问题 | 简短概括，引用或链接获批资料；必要时询问客户意图。 | 添加无依据的保障、价格、期限、表格或投保资格暗示。 | 已批准知识不足时，提出人工协助。 |
| 个性化核保、医疗情况、个案理赔结果、专属保费、折扣或有约束力的报价 | 承认问题，并解释需要有权限的人判断；只问必要且不敏感的转接信息。 | 预测审批、保障或理赔结果；提供医疗建议；承诺报价或处理时限；在聊天中追问病情。 | 提出转人工；立即停止由 AI 作出实质性受限回答。 |
| 客户明确要求人工 | 确认请求，显示“确认／取消”按钮，并允许文字回复。 | 继续推销，或要求客户先回答更多诊断问题。 | 立即提出接管；依已批准流程，仅在客户确认后创建或激活工单。 |
| 系统因其他原因判断需要员工 | 简短说明原因、AI 仍能回答的范围，以及确认／取消选项。 | 在客户确认前说“已提交工单”。 | 先提出再创建；取消后仍保留原有回答限制。 |
| 非人工服务时间 | 仅说明已配置、含时区且真实的服务时段和已知可用情况；可提出留言和有限的安全帮助。 | 编造排队时间、回电期限或开门时间。 | 同样需要确认；仅在确知时说明预计等待。 |
| 已由员工接管的工单 | 有可靠数据时提供安全的状态或转接信息。 | 假装 AI 仍负责对话，或覆盖员工草稿。 | 按员工工作流程更新现有工单。 |

受限问题与购买信号同时出现时，受限边界决定**能回答什么**，购买状态仍独立标注。紧急转人工不会提高购买分。一般理赔流程可根据获批知识回答；个人理赔结果必须交给员工。已公开且仍有效的通用保费可以引用；不能编造个性化报价或折扣。投诉属于服务工作，不自动构成销售机会。

客户可以通过按钮或明确文字确认。孤立的“是”必须与最近一条尚未回答的转人工询问对应；若无法确定所指，或同时有多个待确认问题，应重新询问。取消后清除待确认状态，但不能因此允许模型回答受限问题。转接提议、客户确认、取消、创建工单、员工接管，应分别记录为可审计事件。不要将敏感医疗细节复制进商机档案或员工摘要；原始聊天和调试日志同样需要访问控制、最小化，以及另行商定的保留与脱敏政策。仅禁止衍生字段保存敏感信息，并不能让原始消息存储自动变安全。

## 5. 解读示例（不是新增评测案例）

| 客户最近的话及相关前文 | 拟议标签 | 预期处理 |
| --- | --- | --- |
| “Plus 计划多少钱？” | `price`、`browsing`；没有购买信号 | 如有获批价格资料则简短回答；不得升为高意向线索。 |
| “包含门诊吗？我在比较两个计划。” | `comparison`、`evaluating` | 提供概况和获批详情链接；不假定已经决定购买。 |
| “如果可以打七五折，我就买。” | `price`、`conditional`、`custom_quote_or_negotiation` | 不编造折扣；提出经客户确认的人工接管。 |
| 先说“我想买”，随后说“其实还是三个月后再说吧”。 | `deferred`，时间顾虑 | 降低当前行为分和销售优先级；不称为永久拒绝。 |
| “不，我不买这个了。” | `declined` | 停止销售跟进；不推断其负担不起。 |
| “我有糖尿病，申请会获批吗？” | `eligibility`、`personalized_eligibility_or_underwriting`、`sensitive_data` | 不预测、不继续收集医疗细节；提出人工接管。 |
| “理赔要怎么申请？”与“我的理赔会通过吗？” | 前者是一般 `claims`；后者涉及 `individual_claim_decision` | 前者仅依据获批流程回答；后者不预测结果并提出转人工。 |
| “请帮我转人工。” | `human_request`；购买状态不变 | 立即展示确认／取消；确认后才创建工单。 |
| 没有订单系统集成时，客户说“我昨天已经付钱了”。 | 客户在对话中的自述；不生成完成标签，也不增加购买分 | 说明此处无法核实订单，可提出员工协助；不能宣称保单已正式生效或关闭线索。 |

## 6. 与组员两份草案及现有系统的关系

销售关键词草案有价值的部分，是候选表达、顾虑类别，以及“犹豫不一定抹去兴趣”的洞见。但旧版 30 分模型里的固定关键词加分（包括 0／6／16／25）不能直接搬到目前行为轴 40／30／30 的结构。新规则要求先结合上下文、时间和否定判断购买状态，再赋分。合规草案提供了较好的受限主题清单和员工处理边界。其中“立即接管”的表述需要对应团队已经确定的**提出转接 → 客户确认 → 创建工单**流程，但受限的实质性回答要立即停止。草案对商机档案中敏感信息的禁令，拟扩展到摘要、运行轨迹和日志；这是设计要求，并非声称当前存储已满足。

以后实施时需要核实的现有问题：

- `backend/kernel/scoring.py` 会把价格、保障、比较问题计入购买意向，并使用历史最高意向；即使没有承诺，对话深度仍可能继续增加行为分。
- `backend/kernel/state_machine.py` 对高意向状态下的推迟处理并不一致；一般非销售接触也可能重新激活休眠线索。
- `backend/kernel/hitl.py` 已提出人工接管，`backend/services/conversation.py` 等待客户确认；这一客户交互约定应保留。
- `backend/agent/extraction/model_based.py` 当前没有把完整对话历史传入其模型调用，尽管服务层提供了上下文。单独修复数据库持久化无法解决这一点。
- 原有 20 条案例中，客户自述付款可被视为转化；现有状态机还可以根据模型产生的 `Conversion` 把线索改成 `Closed / Active Customer`。这与拟议的“仅员工可改变正式生命周期”冲突，必须明确决定兼容、迁移和测试方式；本文档没有修改代码。
- 现有 `Priority.HIGH/MEDIUM/LOW` 是销售排序，不是员工待办队列；后者目前尚不存在。

## 7. 验收关口与实施顺序

1. **先审阅本文档。** 与销售及合规相关人员讨论有争议的示例，确认只有员工能改变订单和正式客户生命周期；另行设计员工任务类型及排序，并确定产品知识库的权威来源。
2. **之后建立新评测集。** 包含多轮上下文、歧义、否定、附条件、推迟、新加坡英语表达、可安全回答的理赔流程与不可由 AI 判断的个案理赔，并标出证据片段。在有意识地迁移前，保留旧案例作为回归测试。至少让两个人独立标注部分样本，再裁决分歧；先检查一致性，再把标签当作标准答案。
3. **离线检验规则。** 把人工确认的标签与证据直接输入候选评分和决策规则，检查准确输出及成对不变量：只问价格 < 明确准备购买；附条件 < 条件已满足；准备购买后推迟会降低当前行为分；投诉不代表想买；客户自称付款不能改变正式生命周期；高风险问题不授权 AI 回答。员工任务排序另行评测。报告混淆与分歧，而不只报总体通过率。
4. **数据库和上下文修复后**，用未修改的模型分别运行旧、新评测集。区分模型提取错误、确定性规则错误与知识库缺失；把编造事实和应转人工却未转列为高严重度失败，并单独记录成本与延迟。
5. **仅在证据支持时选择性实施。** 为标签和评分标版本，例如 `two_axis_v2`；从已批准的 Markdown 生成一份机器可读配置，同步更新兼容映射、界面解释、日志及测试。员工队列须在独立的工作流程决策中定义，不能复用 `Priority.HIGH/MEDIUM/LOW`。上线时保留与 `two_axis_v1` 的可逆对照。

下列研究没有提供保险场景专用的分数权重，也没有证明这些规则会提高成交率。上面的数值和优先级限制，是可以在离线、在线评测中证伪的候选方案，而非外部权威结论。

## 参考资料及使用边界

- [CyberAgent SalesTalk 数据集与论文](https://github.com/CyberAgentAILab/salestalk-dataset)：区分继续交谈、提供信息和接受销售目标的意愿。属于模拟的日语销售对话，可借鉴概念划分，不能用于校准新加坡保险分数。
- [Walmart 上下文意图分类研究](https://aclanthology.org/2020.ecnlp-1.6/)：前文有助于理解简短、含糊的购物表达，支持使用多轮上下文。
- [ABCD 客服对话语料](https://github.com/asappresearch/abcd)：包含场景及受政策约束的行动顺序，可借鉴明确的决策边界，但不是我们的保险政策。
- [CLINC 范围外意图数据集](https://github.com/clinc/oos-eval)：支持 `unknown` 或暂不判断的路径，避免强行归类；数据主要来自通用领域的单轮表达。
- [CoSEM 新加坡英语语料](https://github.com/wdwgonzales/CoSEM)：可帮助设计本地语言变体测试，但不是销售或保险语料。复用原文之前必须检查非商业许可限制。
- [新加坡人寿保险协会 2024 年信任调查](https://www.lia.org.sg/media/4390/iccsc_insurance-trust-indicator-study-2024_final-report.pdf)：提供本地保险服务和信任背景，不能证明具体评分权重或 WhatsApp 咨询量假设。
- [新加坡人寿保险协会保险术语表](https://www.lia.org.sg/tools-and-resources/insurance-terms/)：仅供理解通用保险术语，绝不能当作 CareSure 产品事实来源。
- [InsuranceQA](https://github.com/shuzi/insuranceqa) 与 [JDDC](https://aclanthology.org/2020.lrec-1.58/)：分别可借鉴保险提问方式和多轮电商对话，但存在领域及许可限制。

更完整的资料分析与组员草案评议见[对话意图研究与修订计划（英文）](conversation-intent-research-and-revision-plan.md)。在将拟议的在线评测解释为模型能力测试前，应先完成[持久化与评测修复计划（英文）](persistence-repair-plan.md)中的相关修复。
